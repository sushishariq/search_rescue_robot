Search-and-Rescue Marker Finder – Design

ROS 2 Humble · Gazebo Classic 11 · Nav2 · OpenCV 4.5.4 (cv2.aruco) · Docker  |  Repository: github.com/sushishariq/search_rescue_robot

A TurtleBot3 Waffle patrols a 12 × 10 m simulated building with four rooms. It localizes with AMCL on a map built once with slam_toolbox, follows a Nav2 waypoint route, detects ArUco victim markers with classical OpenCV, projects each detection into the map frame through TF, and keeps a deduplicated victim registry that is exposed through the /get_victims service and exported to JSON/CSV. The whole stack starts with docker compose up sar, which runs a single mission launch file.

2. Environment and sensor wiring

The world and markers are generated by scripts, so marker size and positions are defined once and the ground truth is known. Each marker is a thin static box textured with a DICT_4X4_50 image: a 0.20 m black square inside a 0.05 m white quiet zone. The robot is a copy of the TurtleBot3 Waffle with three changes, each found by measuring:

  • Optical frame: the stock camera plugin stamps images with camera_rgb_frame (x forward), while OpenCV poses are in the optical frame (z forward). frame_name is set to camera_rgb_optical_frame so the TF chain is correct without a rotation patch in code.
  • Camera pose: the SDF camera sat 1 cm below the URDF camera. The SDF pose was set to match, and the URDF rotation uses exact π/2 values.
  • Resolution and lidar: the camera runs at 640×480 and 15 Hz instead of 1920×1080 at 30 Hz. camera_info.yaml follows from the field of view: f = 640 / (2·tan(1.02974/2)) = 565.6 px, c = (320.5, 240.5), zero distortion. The lidar range was raised to 8 m at 10 Hz so SLAM and AMCL see through doorways.

3. Camera-to-map TF chain

cv2.aruco.detectMarkers finds the four corners of each marker, and estimatePoseSingleMarkers solves for the marker pose from the known side length (0.20 m) and K. The result, a rotation vector and translation vector, is expressed in camera_rgb_optical_frame: x right, y down, z forward (REP-103 camera convention). The detector puts this pose in a PoseStamped with the image's header (frame and timestamp) and calls tf2 Buffer.transform(pose, "map"). tf2 then composes these transforms:

p_map = Tmap←odom(t) · Todom←base(t) · Tbase←optical · p_optical     (t = image timestamp)

Why the image timestamp matters. The robot keeps moving while an image is processed. Looking up TF at the image time uses the robot pose at the moment the photo was taken; using "latest" would place markers wrongly whenever the robot turns. Why REP-105 splits the chain. A TF frame can have only one parent, so odometry owns odom → base (smooth, drifting) and AMCL owns map → odom (the correction). Implementation detail. The TF subscriptions and the image callback are in separate callback groups on a multi-threaded executor, so TF keeps arriving while an image callback waits up to 0.2 s for a transform. A first single-threaded version fell behind TF and failed with extrapolation errors. Detections farther than 3.5 m or smaller than 20 px per side are dropped because pose noise grows with range.

4. Deduplication logic

The detector publishes one Victim message per marker per frame, so a single marker yields 50–370 detections during a patrol. registry_core.py (pure Python, unit-tested) reduces them to one entry per victim. For each detection (id, x, y, range):

  1. Same ID → same victim. Merge into the nearest victim with that ID. Guard: if that victim is already confirmed and the detection is more than 1.0 m away, reject it as an outlier (for example, a transform taken during a localization jump).
  2. Nearby position → same victim. Otherwise, if any victim lies within 0.5 m, merge into it. This absorbs a misread ID. A victim's ID is the majority vote of its observations, so a rare misread cannot rename it.
  3. Otherwise → new victim.

Position estimate: a weighted running mean with weight 1/range², so close, more accurate observations dominate (the minimum range used for weighting is 0.5 m). Confirmation: a victim is reported by the service and written to file only after 3 observations, which filters one-frame false positives. Why 0.5 m: it is several times the observed projection error (≈ 8 cm) yet far below the marker spacing (> 2 m), so two real victims cannot merge. Results are written atomically every 2 s while they change and again on shutdown.

6. Navigation and error sources

Map: built with slam_toolbox (online async) while Nav2 drove to clicked goals. Because Gazebo's diff drive reports odometry in world coordinates, the saved map frame coincides with the world frame, so results compare directly with ground truth.

AMCL: alpha1–4 = 0.05 (low odometry noise in simulation), 120 beams, updates every 0.1 m / 0.1 rad, initial pose preset. Measured pose error is 5–10 cm, the main contributor to projection error. Pose estimation alone is within 1 cm at 1.5 m.

Nav2: inflation radius 0.45 m with scaling factor 5 so the 1.2 m doorways stay passable; waypoint poses face each marker from about 1.7 m, with a 2 s pause at each.

Limitations: marker textures ignore lighting; the stock Waffle can yaw slowly for a few seconds after stopping (contact physics; TF follows the true motion).
