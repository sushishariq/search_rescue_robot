# Search-and-Rescue Marker Finder (ROS 2 Humble)

A TurtleBot3 Waffle patrols a simulated building with Nav2, localizes with AMCL on a pre-built map, detects ArUco "victim" markers with classical OpenCV, projects them into the map frame through TF, and keeps a deduplicated victim registry exposed as a ROS 2 service.

Everything runs in Docker: ROS 2 Humble, Gazebo Classic 11, Nav2, slam_toolbox, OpenCV 4.5.4 (`cv2.aruco`), cv_bridge.

## Requirements

- Linux host with Docker and Docker Compose v2
- X11 display (Gazebo and RViz windows)
- Intel/AMD GPU via `/dev/dri` (for NVIDIA, replace `devices:` with the NVIDIA container runtime)

## Build and run

```bash
git clone https://github.com/sushishariq/search_rescue_robot.git
cd search_rescue_robot
docker compose build sar
xhost +local:root
docker compose up sar
```

`docker compose up sar` runs `ros2 launch sar_bringup mission.launch.py`, which starts:

Gazebo (building world + robot) → map_server + AMCL → Nav2 → ArUco detector → victim registry → patrol.

The robot visits 7 waypoints, then prints the registry. Results are written to `src/sar_mission/results/victims.json` and `victims.csv` on the host.

Query the registry at any time:

```bash
docker compose exec sar bash -c "source /sar_ws/install/setup.bash && ros2 service call /get_victims sar_interfaces/srv/GetVictims"
```

Stop: `Ctrl+C`, then `docker compose down`.

## How it works

### Camera → map TF chain

1. `cv2.aruco.detectMarkers` finds the marker corners, and `estimatePoseSingleMarkers` (marker side 0.20 m, K from `camera_info.yaml`) gives the marker pose in `camera_rgb_optical_frame` (z forward, x right, y down).
2. The pose is stamped with the image timestamp and transformed with `tf2` to `map`:
   - `camera_rgb_optical_frame → camera_rgb_frame → camera_link → base_link → base_footprint` (static, URDF via robot_state_publisher)
   - `base_footprint → odom` (Gazebo diff-drive odometry)
   - `odom → map` (AMCL)
3. Using the image timestamp means the robot pose at the moment the photo was taken is used, not the pose when processing finished.

### Deduplication (`sar_mission/registry_core.py`)

For each detection `(id, x, y, range)`:

1. **Same ID** as a known victim → merge. If that victim is already confirmed and the detection is more than 1.0 m away, reject it as an outlier.
2. **Else, within 0.5 m** of a known victim (any ID) → merge. This catches a misread ID; the victim's ID is the majority vote.
3. **Else** → new victim.

The position is a running weighted mean with weight `1/range²`, since near observations are more accurate. A victim is reported after 3 observations, which filters one-frame false positives. The rules are unit-tested in `sar_mission/test/test_registry_core.py`.

### Simulation setup

- **Robot:** a copy of the TurtleBot3 Waffle, with the camera set to 640×480 at 15 Hz. The plugin `frame_name` is changed to `camera_rgb_optical_frame` (stock publishes the body frame), and the camera pose now matches the URDF. The lidar is set to 8 m range at 10 Hz.
- **World:** a 12 × 10 m building with 4 rooms, 2 obstacles and 6 ArUco markers (DICT_4X4_50, 0.20 m). It is generated by `sar_bringup/scripts/generate_world.py` and `generate_aruco_models.py`.
- **Map:** built once with slam_toolbox (online async), with Nav2 driving to clicked goals. The map frame coincides with the Gazebo world frame, so results compare directly with ground truth.

- `slam.launch.py`: mapping
- `nav.launch.py`: AMCL + Nav2
- `perception.launch.py`: detector only

### Rebuilding the map

```bash
ros2 launch sar_bringup slam.launch.py      # drive with "Nav2 Goal" in RViz
cd /sar_ws/src/sar_bringup/maps
ros2 run nav2_map_server map_saver_cli -f building --ros-args -p use_sim_time:=true
ros2 service call /slam_toolbox/serialize_map slam_toolbox/srv/SerializePoseGraph "{filename: '/sar_ws/src/sar_bringup/maps/building'}"
```

## Known limitations

- **Robot settling after a stop:** after Nav2 publishes zero velocity, the stock Waffle model can yaw a few tens of degrees over about 20 s. That's Gazebo contact physics. TF follows the true motion, so projections stay correct.
- **Marker lighting:** marker textures use `lighting off` so detection doesn't depend on scene lighting.
- **RViz on exit:** RViz2 may print a segfault on shutdown, which is a known RViz2 issue and harmless.
